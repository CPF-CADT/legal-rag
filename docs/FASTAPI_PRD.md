# LegalRAG FastAPI MVP — Product Requirements Document

## 1. Product goal

Expose the existing Cambodian legal retrieval and grounded-answer system through
a small HTTP API that can be consumed by the React client or other clients.

The MVP has two user-facing capabilities:

1. Search a legal question and return ranked results with the complete legal
   article text and source metadata.
2. Submit a legal question and return an LLM-generated Khmer summary grounded
   only in the retrieved legal articles.

The API is an application layer over the existing dense retrieval and LLM
services. It must not rebuild embeddings, modify OCR text, or implement
retrieval logic inside route handlers.

## 2. Scope

### In scope

- FastAPI application with typed request and response models.
- `POST /api/search` for semantic retrieval.
- `POST /api/summarize` for retrieval plus grounded LLM summarization.
- `GET /health` for liveness and `GET /ready` for dependency readiness.
- Reuse of `DenseRetriever`, `AnswerService`, and existing LLM adapters.
- Khmer query validation and stable JSON error responses.
- Dependency injection and application lifespan loading for the retriever and
  LLM service.
- Unit tests for API validation, service orchestration, response mapping, and
  error handling.
- OpenAPI documentation generated by FastAPI.

### Out of scope for MVP

- User authentication, authorization, rate limiting, or billing.
- New retrieval algorithms, BM25, hybrid search, reranking, or re-embedding.
- OCR, crawling, index construction, or corpus administration endpoints.
- Conversation memory and streaming responses.
- Direct exposure of local file paths, Chroma internals, prompts, API keys, or
  stack traces.

## 3. Existing-system assumptions

- The production retrieval unit is a BGE-M3 ChromaDB chunk.
- The user-facing result is the complete parent legal article, not only the
  matching chunk.
- The current retriever is configured for a bounded top-k result set. “Full
  list” means the full article body and metadata for every returned result, not
  the entire corpus in one response.
- The current `AnswerService` owns evidence thresholding and grounded prompt
  execution.
- Retrieval/index files are available at runtime and are loaded once during
  application startup or the first dependency initialization.

## 4. API contract

### 4.1 `POST /api/search`

Searches the indexed legal corpus and returns complete ranked articles.

Request:

```json
{
  "query": "តើនិយោជកមានកាតព្វកិច្ចអ្វីខ្លះ?",
  "top_k": 5
}
```

Rules:

- `query` is required, trimmed, and must not be blank.
- `top_k` defaults to 5 and has a server-enforced maximum, initially 20.
- The service may use the existing query-correction variants internally.

Response:

```json
{
  "query": "តើនិយោជកមានកាតព្វកិច្ចអ្វីខ្លះ?",
  "items": [
    {
      "rank": 1,
      "article_id": "document-article",
      "document_id": "document",
      "title": "...",
      "article_number": "...",
      "article_text": "...",
      "source_url": "...",
      "pdf_url": "...",
      "score": 0.82,
      "matched_chunks": []
    }
  ],
  "count": 1
}
```

`article_text` must contain the complete article body. Server-only paths and
raw persistence objects must never be returned.

### 4.2 `POST /api/summarize`

Retrieves relevant legal articles and asks the configured LLM to summarize them
in Khmer.

Request:

```json
{
  "query": "តើនិយោជកមានកាតព្វកិច្ចអ្វីខ្លះ?",
  "top_k": 5
}
```

Response:

```json
{
  "query": "តើនិយោជកមានកាតព្វកិច្ចអ្វីខ្លះ?",
  "summary": "...",
  "sources": [],
  "has_sufficient_evidence": true
}
```

If evidence is insufficient, return HTTP 200 with `summary: null`, an empty
source list, and `has_sufficient_evidence: false`, unless the existing service
contract is explicitly changed. LLM failures should become a stable 502-style
application error and must not expose provider details.

### 4.3 Operational endpoints

- `GET /health` returns process liveness without requiring the embedding model.
- `GET /ready` confirms that configured retrieval dependencies are loaded and
  usable. It returns a non-2xx response when the index or LLM configuration is
  unavailable.

## 5. Error contract

All application errors use one shape:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "query must not be blank",
    "request_id": "..."
  }
}
```

Minimum codes:

- `VALIDATION_ERROR` — invalid request data.
- `RETRIEVAL_UNAVAILABLE` — index/model cannot be loaded.
- `LLM_UNAVAILABLE` — summary generation failed.
- `INTERNAL_ERROR` — unexpected server failure.

Do not return local paths, credentials, provider payloads, or Python tracebacks.

## 6. Non-functional requirements

- Use a layered architecture: API/router → application service → domain DTOs
  and ports → infrastructure adapters.
- Keep route handlers thin and framework-independent business logic testable.
- Load heavyweight models once per process, not once per request.
- Make configuration environment-driven and keep secrets out of source control.
- Preserve current Telegram behavior while sharing retrieval and generation
  services.
- Add structured request logging without logging full legal queries or LLM
  prompts by default.
- Use async route functions only where the underlying work is safely offloaded;
  do not pretend synchronous model inference is non-blocking.

## 7. Acceptance criteria

- A valid search request returns ranked complete articles from the existing
  index.
- A blank query returns a clear 422 validation response.
- A valid summarize request returns a grounded Khmer summary and source list.
- Insufficient evidence does not produce a fabricated answer or citations.
- Startup/readiness failures are observable and return stable errors.
- API tests run without loading real model weights by using fake ports/adapters.
- An integration test can run against configured local retrieval/LLM fixtures or
  explicit mocks.
- Existing retrieval and Telegram tests remain passing.
- `/docs` and `/openapi.json` describe the two business endpoints and models.
